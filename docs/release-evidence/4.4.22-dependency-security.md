# Mastodon 4.4.22 dependency and security evidence

Generated on 2026-08-12 (Asia/Tokyo) from the Paon 4.4 compatibility
checkout. This document records the exact scan target and command results; it
does not by itself admit an image to production.

## Reference and candidate images

- The inspected official image was
  `ghcr.io/mastodon/mastodon:v4.4.22` at repository digest
  `sha256:91c5a9fa6e6f970f7e96c7b6583d0eba56b570d08c8c8557c98536685feee0c1`
  (local image ID
  `sha256:dadb327b665a7be2085667f88ee3437fa5e981f00553e51bed4beab34c3be89b`).
  Its runtime reports FFmpeg `7.1.5`, matching the `FFMPEG_VERSION=7.1.5`
  source pin in the upstream v4.4.22 Dockerfile.
- After the final source audit and the complete repository gates, the
  `docker build --pull --tag paon:4.4.22-compat-final .` command produced the
  exact candidate image scanned below:
  `sha256:faff3fb372b031bde510777c697cd3933995f43dbcaf35acf7063e7c9bec21ee`
  (`linux/amd64`, 1,252,697,416 bytes). Dependency layers were reused, while
  both source-copy steps and the Go and production Rspack builds ran again.
- The Paon candidate is Debian 13.6 and contains FFmpeg/ffprobe
  `7.1.5-0+deb13u1` and libvips `8.16.1-1+deb13u1`. `ldd` confirms that the
  selected `/usr/local/bin/paon` binary uses `libvips.so.42`; the native Go
  processor remains the Dockerfile's explicit build fallback.

The image is an exact, identified scan target built from the source frozen for
these gates, but it is a compatibility candidate rather than an immutable
published release. Rebuild and repeat the same scans after the release commit
itself is frozen; later source changes are not covered by this image ID.

## Dependency delta from the 4.3 evidence

- The branch retains the verified Go 1.25.12/module baseline recorded for
  4.3.23. Relative to the 4.4 branch point, `go.mod` and `go.sum` do not need a
  compatibility-only change. `go mod verify` and `go mod tidy -diff` are clean
  against the current module graph.
- The frontend lock delta adds `lande` 1.0.10 and its `toygrad` 2.6.0
  dependency for the 4.4 language-detection behavior. The existing Paon
  React/Rspack dependency graph is retained instead of importing Mastodon's
  Vite UI dependency graph.
- The current advisory databases still report no reachable Go vulnerability
  and no high or critical frontend finding. The same moderate development
  server chain documented for 4.3 remains. The Debian all-findings inventory
  moved from 210 (195 high, 15 critical) in the earlier evidence to 211 (196
  high, 15 critical). All 211 currently lack a fixed Debian package; the
  one-finding increase reflects the newer advisory database snapshot and must
  not be interpreted as a clean full inventory.

Conversely, absence of a Debian fixed version is not a waiver. Release owners
must evaluate the exposed media/parsing paths and either accept the risk or
move to a package/base image that provides fixes.

## Reproduction commands

The image archive and Trivy database were temporary files under ignored
`.release-cache/`. To prevent a scanner from reading the application image
while it had network access, database download and image inspection were
separate steps. The actual scan mounted the image read-only and used
`--network none`.

```bash
rtk env TMPDIR="$PWD/.go-tmp" GOTMPDIR="$PWD/.go-tmp" \
  GOCACHE="$PWD/.go-buildcache" GOMODCACHE="$PWD/.go-modcache" \
  go run golang.org/x/vuln/cmd/govulncheck@latest ./...
rtk env TMPDIR="$PWD/.go-tmp" GOTMPDIR="$PWD/.go-tmp" \
  GOCACHE="$PWD/.go-buildcache" GOMODCACHE="$PWD/.go-modcache" \
  go mod verify
rtk env TMPDIR="$PWD/.go-tmp" GOTMPDIR="$PWD/.go-tmp" \
  GOCACHE="$PWD/.go-buildcache" GOMODCACHE="$PWD/.go-modcache" \
  go mod tidy -diff
rtk yarn audit --groups dependencies --json
rtk yarn check --integrity --ignore-scripts

rtk docker image inspect ghcr.io/mastodon/mastodon:v4.4.22
rtk docker run --rm --entrypoint ffmpeg \
  ghcr.io/mastodon/mastodon:v4.4.22 -version
rtk docker build --pull --tag paon:4.4.22-compat-final .
rtk docker image inspect paon:4.4.22-compat-final
rtk docker run --rm --entrypoint ffmpeg paon:4.4.22-compat-final -version
rtk docker run --rm --entrypoint ffprobe paon:4.4.22-compat-final -version
rtk docker run --rm --entrypoint dpkg-query paon:4.4.22-compat-final \
  -W -f='${Package}\t${Version}\n' ffmpeg libvips42t64

rtk mkdir -p .release-cache/trivy-cache
rtk docker save --output .release-cache/paon-4.4.22-compat-final.tar \
  paon:4.4.22-compat-final
rtk docker run --rm --user 1000:1000 \
  --volume "$PWD/.release-cache/trivy-cache:/cache" \
  aquasec/trivy:latest image --download-db-only --cache-dir /cache --no-progress
rtk docker run --rm --network none --user 1000:1000 \
  --volume "$PWD/.release-cache/paon-4.4.22-compat-final.tar:/audit/image.tar:ro" \
  --volume "$PWD/.release-cache/trivy-cache:/cache" \
  aquasec/trivy:latest image --input /audit/image.tar --cache-dir /cache \
  --skip-db-update --scanners vuln --severity HIGH,CRITICAL \
  --ignore-unfixed --exit-code 1 --no-progress --format table
rtk docker run --rm --network none --user 1000:1000 \
  --volume "$PWD/.release-cache/paon-4.4.22-compat-final.tar:/audit/image.tar:ro" \
  --volume "$PWD/.release-cache/trivy-cache:/cache" \
  aquasec/trivy:latest image --input /audit/image.tar --cache-dir /cache \
  --skip-db-update --scanners vuln --severity HIGH,CRITICAL \
  --no-progress --format json
```

## Release disposition

The reachable Go gate, frontend high/critical gate, upstream FFmpeg floor, and
fixable-container gate are clean for the identified candidate. Production
admission remains blocked on an explicit disposition for the one moderate
frontend build-chain finding and the 211 unfixed Debian high/critical package
findings. Rebuild from the frozen release commit, update the advisory database,
and scan that exact immutable image again before publishing it.

No exporter credentials, environment values, request bodies, URLs, query text,
tokens, or application data were captured. The temporary image archive and
scanner database are not release artifacts and are removed after recording
this evidence.
