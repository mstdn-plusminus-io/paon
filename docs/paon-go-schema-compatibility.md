# Paon Go schema compatibility

`internal/paon/migrate/schema.sql` is the reviewed, embedded PostgreSQL schema snapshot. Ruby and Rails are not required to initialize or validate a database.

| Starting state                                               | Supported action                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Empty PostgreSQL database                                    | `paon-migrate` creates the complete Mastodon 4.4.22-compatible schema, functions, sequences, indexes, foreign keys, materialized views, metadata, all 539 migration markers, and production seed rows.                                                                                                                                                                                                                                                         |
| Compatible schema version `20250627132728` (Mastodon 4.4.22) | `paon-migrate` validates the complete Paon schema and exits without changing data.                                                                                                                                                                                                                                                                                                                                                                            |
| Mastodon 4.3.23 schema `20241007071624`                      | Run `paon-migrate --phase=expand`; after all 4.3 writers are stopped run `--phase=backfill`, `--phase=validate`, and finally `--phase=contract --acknowledge-contract`. Backfill imports legacy Redis tag trends; it fails closed without a Redis source unless `MIGRATION_SKIP_TAG_TREND_BACKFILL=true` explicitly asserts that the source is empty or disposable.                                                                                                 |
| Mastodon 4.2.19 / Paon schema `20230907150100`               | Use the same phase sequence. Paon completes the reviewed 4.3 phases before advancing through 4.4; an acknowledged contract run can finish both inventories in one fenced maintenance window. A bare invocation always defaults to expand. `PAON_MIGRATION_PHASE` and `PAON_MIGRATION_ACKNOWLEDGE_CONTRACT=true` are the non-interactive equivalents.                                                                                                           |
| Any older/newer/partial schema                               | Refused. Upgrade or downgrade with a release that explicitly supports that starting version. Unknown/future markers and final markers with an incomplete 4.3 or 4.4 inventory fail closed.                                                                                                                                                                                                                                                                     |

Migration execution uses a PostgreSQL transaction-scoped advisory lock. Fresh initialization is atomic; expand, backfill, validate, and contract are each atomic and commit independently so a later failure does not roll back an already accepted phase. Concurrent invocations serialize, every upstream migration version is recorded separately, GORM AutoMigrate remains disabled, and the snowflake `timestamp_id` function receives a new random salt for each fresh database. Re-running any completed phase is a no-op. Before any upgrade write, a read-only prerequisite guard verifies every legacy relation required by Paon's final contract plus the 4.2 columns directly used by phased SQL. A later target verifies all prior phase markers before mutation; current admission requires the complete reviewed marker inventory, and unknown or future post-4.2 markers are refused. Duplicate, locale, notification-policy, OAuth-scope, and OTP work runs in bounded 500-row batches, while the enclosing phase transaction preserves all-or-nothing rollback. Duplicate cleanup keeps the lowest ID while regular unique-index creation prevents a concurrent writer from reopening the duplicate window. Large-table indexes are deliberately created in the transaction and therefore take a write-blocking lock; measure the maintenance-window lock duration, replica lag, disk headroom, and table rewrite behavior on production-sized staging data before production admission.

The 4.3 backfill is batched and idempotent. It converts `fr-QC` to `fr-CA`, legacy interaction settings to notification policy v2, `read:me` to `profile`, and legacy Rails or Paon TOTP secrets to Rails 7.1 Active Record Encryption. Enabled 2FA rows with an invalid legacy secret abort by default and report only the user ID. `MIGRATION_IGNORE_INVALID_OTP_SECRET=true` is an explicit data-loss escape hatch and must be recorded in the deployment log.

The 4.4 expand phase adds the quote, translated-rule, tag-trend, terms-of-service, instance-note, FASP, annual-report, Web Push, age, and supporting catalog. Backfill atomically upserts legacy Redis tag-trend scores into PostgreSQL and only removes the source keys after the database transaction commits. Validate cleans and locks in upstream `NOT NULL` contracts and rejects invalid quote/settings/OTP/import state. Contract drops the legacy imports table, old settings ownership columns and indexes, and legacy encrypted OTP columns, then records schema SHA-1 `b53e3b8de778cd1b53158326b97afa9368f3237e`. The one-way DynamoDB quote import is a separate post-schema administrative operation; DynamoDB is never a 4.4 runtime source of truth.

The validate phases perform their data/FK scans and finalize `NOT NULL` only after old writers are fenced. Each contract phase re-runs its data checks, applies destructive removals, and runs the applicable schema guard before the transaction commits. Contract cannot run without both the explicit phase and acknowledgment. Expand/backfill/validate use phase-specific marker and data checks because intentionally retained legacy objects would fail the final guard. See `docs/mastodon-4.3-migration-inventory.md`, `docs/mastodon-4.4-migration-inventory.md`, and `docs/paon-go-cutover.md` for per-version traceability and backup/rollback boundaries.

When the database contract changes:

1. update and review `internal/paon/migrate/schema.sql`;
2. add an explicit versioned upgrade path before changing `CurrentSchemaVersion`;
3. update models and startup schema guards for tables, columns, defaults, indexes, keys, functions, sequences, and views;
4. run migration integration tests against an empty database and every supported starting version;
5. document rollback and cutover behavior.
