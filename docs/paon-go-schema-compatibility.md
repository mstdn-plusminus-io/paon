# Paon Go schema compatibility

`internal/paon/migrate/schema.sql` is the reviewed, embedded PostgreSQL schema snapshot. Ruby and Rails are not required to initialize or validate a database.

| Starting state                                               | Supported action                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Empty PostgreSQL database                                    | `paon-migrate` creates the complete Mastodon 4.4.22-compatible schema, functions, sequences, indexes, foreign keys, materialized views, metadata, all 539 migration markers, and production seed rows.                                                                                                                                                                                                                                                         |
| Compatible schema version `20250627132728` (Mastodon 4.4.22) | `paon-migrate` idempotently reconciles history-independent canonical FK names and the `timestamp_id` body, then validates the runtime schema. `paon-migrate --check` is read-only and rejects incompatible runtime objects.                                                                                                                                                                   |
| Mastodon 4.3.23 schema `20241007071624`                      | Run `paon-migrate --phase=expand`; after all 4.3 writers are stopped run `--phase=backfill`, `--phase=validate`, and finally `--phase=contract --acknowledge-contract`. Backfill imports legacy Redis tag trends; it fails closed without a Redis source unless `MIGRATION_SKIP_TAG_TREND_BACKFILL=true` explicitly asserts that the source is empty or disposable.                                                                                                 |
| Mastodon 4.2.19 / Paon schema `20230907150100`               | Use the same phase sequence. Paon completes the reviewed 4.3 phases before advancing through 4.4; an acknowledged contract run can finish both inventories in one fenced maintenance window. A bare invocation always defaults to expand. `PAON_MIGRATION_PHASE` and `PAON_MIGRATION_ACKNOWLEDGE_CONTRACT=true` are the non-interactive equivalents.                                                                                                           |
| Any older/newer/partial schema                               | Refused. Upgrade or downgrade with a release that explicitly supports that starting version. Unknown/future markers and final markers with an incomplete 4.3 or 4.4 inventory fail closed.                                                                                                                                                                                                                                                                     |

Migration execution uses a PostgreSQL transaction-scoped advisory lock. Fresh initialization is atomic; expand, backfill, validate, and contract are each atomic and commit independently so a later failure does not roll back an already accepted phase. Concurrent invocations serialize, every upstream migration version is recorded separately, GORM AutoMigrate remains disabled, and the snowflake `timestamp_id` function receives a new random salt for each fresh database. Re-running a canonical completed phase is a no-op. Before any upgrade write, a read-only prerequisite guard verifies every legacy relation required by Paon's final contract plus the 4.2 columns directly used by phased SQL. A later target verifies all prior phase markers before mutation; current admission requires the complete reviewed marker inventory, canonical Rails constraint names, and no unknown or future post-4.2 markers.

Strict PostgreSQL 14 and 15 catalog goldens are route-specific because Mastodon itself produces different physical catalogs for fresh loads and upgrades. They cover physical column positions and dropped slots, types/defaults/nullability, index and constraint names and definitions, function text, views, sequence ownership, all migration markers, and Active Record metadata. The retained 4.3 goldens fix the v4.2.19, v4.3.23 fresh, and v4.2-to-v4.3 boundaries. The 4.4 goldens independently fix Mastodon 4.4.22 fresh, v4.3.23-to-v4.4.22, and v4.2.19-to-v4.4.22 at all 539 markers. Only instance-specific OIDs/storage statistics/current sequence values and the random `timestamp_id` salt are normalized.

For databases already marked `20241007071624`, reconciliation is intentionally limited to canonical FK names and the function body, whose target values do not depend on database history. It does not guess fresh/staged provenance from dropped-column slots, schema hashes, or sequence ownership: legitimate long-lived and dump/restored Mastodon databases vary in those details. A database created by an older Paon build with a non-canonical physical layout requires a reviewed dump/restore rehearsal before claiming byte-for-byte catalog parity. Data already deleted or text already rewritten by an older migration cannot be reconstructed by catalog reconciliation.

The 4.4 contract runs the same safe reconciliation after creating all 4.4 foreign keys and before its final schema guard. This allows a supported 4.3.23 database created by an older Paon build to advance without weakening the 143 canonical-name FK contract.

Duplicate, locale, notification-policy, OAuth-scope, and OTP work runs in bounded 500-row batches, while the enclosing phase transaction preserves all-or-nothing rollback. Unique indexes are attempted without cleanup when PostgreSQL can accept the existing rows; cleanup runs only for a real non-NULL uniqueness violation and then follows Mastodon's lowest-ID behavior, including its treatment of NULL groups. Locale timestamps, substring scope replacement, whitespace, and Ruby/Oj truthiness follow the upstream data migrations. Large-table indexes are deliberately created in the transaction and therefore take a write-blocking lock; measure the maintenance-window lock duration, replica lag, disk headroom, and table rewrite behavior on production-sized staging data before production admission.

The 4.3 backfill is batched and idempotent. It converts `fr-QC` to `fr-CA` without touching `users.updated_at`, migrates legacy interaction settings with Ruby truthiness, applies Mastodon's substring `read:me` to `profile` replacement, and converts legacy Rails or Paon TOTP secrets to Rails 7.1 Active Record Encryption. Enabled 2FA rows with an invalid legacy secret abort by default and report only the user ID. `MIGRATION_IGNORE_INVALID_OTP_SECRET=true` is an explicit data-loss escape hatch and must be recorded in the deployment log.

The 4.4 expand phase adds the quote, translated-rule, tag-trend, terms-of-service, instance-note, FASP, annual-report, Web Push, age, and supporting catalog. Backfill atomically upserts legacy Redis tag-trend scores into PostgreSQL and only removes the source keys after the database transaction commits. Validate cleans and locks in upstream `NOT NULL` contracts and rejects invalid quote/settings/OTP/import state. Contract drops the legacy imports table, old settings ownership columns and indexes, and legacy encrypted OTP columns, then records the final marker without overwriting the source route's schema SHA. Fresh 4.4 uses `b53e3b8d...`; v4.3 and v4.2 lineages retain `d03e3ba5...` and `7d508622...` respectively. The one-way DynamoDB quote import is a separate post-schema administrative operation; DynamoDB is never a 4.4 runtime source of truth.

The validate phases perform their data/FK scans and finalize `NOT NULL` only after old writers are fenced. Each contract phase re-runs its data checks, applies destructive removals, and runs the applicable schema guard before the transaction commits. Contract cannot run without both the explicit phase and acknowledgment. Expand/backfill/validate use phase-specific marker and data checks because intentionally retained legacy objects would fail the final guard. See `docs/mastodon-4.3-migration-inventory.md`, `docs/mastodon-4.4-migration-inventory.md`, and `docs/paon-go-cutover.md` for per-version traceability and backup/rollback boundaries.

When the database contract changes:

1. update and review `internal/paon/migrate/schema.sql`;
2. add an explicit versioned upgrade path before changing `CurrentSchemaVersion`;
3. update models and startup schema guards for tables, columns, defaults, indexes, keys, functions, sequences, and views;
4. run migration integration tests against an empty database and every supported starting version;
5. document rollback and cutover behavior.
