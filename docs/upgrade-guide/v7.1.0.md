# Paon 7.0.x から 7.1.0 へのアップグレード

Docker Compose で稼働している Paon 7.0.x を 7.1.0 に更新する手順です。リポジトリの `docker-compose.yml` にある `web`、`worker`、`db-migrate`、`db` を使用します。サービス名や接続設定を変更している場合は、自分の構成に読み替えてください。

7.1.0 では、DB を Mastodon 4.2 系から 4.3.23 相当のスキーマに更新します。新しいイメージの取得に加えて、暗号鍵の設定と全フェーズのマイグレーションが必要です。旧バージョンの全 web・worker を停止するため、メンテナンス時間を確保してください。

## 1. 設定と旧イメージを保存する

Compose ファイルのあるディレクトリで作業します。更新前の Compose ファイル、使用している override ファイル、`.env`、`.env.production` を安全な場所にバックアップしてください。設定ファイルには秘密情報が含まれるため、第三者から読めない権限で保存します。

稼働中のイメージのタグと digest も記録し、同じイメージに戻せるようにします。`latest` などの可変タグだけでは旧イメージを特定できません。

## 2. 暗号鍵を設定する

`.env.production` に次の3つが設定されていることを確認します。7.1.0 の production 起動では、2要素認証の利用者がいない場合も必要です。

```dotenv
ACTIVE_RECORD_ENCRYPTION_PRIMARY_KEY=...
ACTIVE_RECORD_ENCRYPTION_DETERMINISTIC_KEY=...
ACTIVE_RECORD_ENCRYPTION_KEY_DERIVATION_SALT=...
```

未設定の項目には、それぞれ独立した32バイト以上のランダム値を設定します。例えば、次のコマンドを項目ごとに実行して生成した値を使用できます。`...` をそのまま設定しないでください。

```bash
openssl rand -hex 32
```

すでに設定済みの値は変更せず、既存の `OTP_SECRET` と `SECRET_KEY_BASE` も引き継いでください。新しい暗号鍵は2要素認証の秘密情報の移行に使用するため、移行後も同じ値を保持します。追加した鍵を含む設定もバックアップしてください。

標準の Compose 構成では、`web`、`worker`、`db-migrate` が `.env.production` を読み込みます。独自構成では、この3サービスに同じ暗号鍵と同じ DB 接続設定を渡してください。

## 3. 7.1.0 のイメージを取得する

7.1.0 のイメージが公開されていることを確認し、`web`、`worker`、`db-migrate` の `image` をすべて同じバージョンに変更します。AMD64 向けの指定例は次のとおりです。ARM64 環境では、公開されている対応アーキテクチャのタグを指定してください。

```yaml
image: plusminusio/paon:7.1.0
```

設定を検証してからイメージを取得します。この段階では稼働中のコンテナは更新されません。

```bash
docker compose --profile setup config --quiet
docker compose --profile setup pull web worker db-migrate
```

取得に失敗した場合は、旧コンテナを停止せずに原因を解消してください。

## 4. 旧プロセスを停止して DB をバックアップする

```bash
docker compose stop web worker
```

別ホストのレプリカや定期実行ジョブも含め、この DB に書き込む旧バージョンの Paon をすべて停止します。PostgreSQL、Redis、Meilisearch は稼働させたままにします。

停止後に PostgreSQL のバックアップを取得します。標準構成では、次のコマンドでコンテナ内の `POSTGRES_USER` と `POSTGRES_DB` を使用できます。外部 DB を使用している場合は、その環境のバックアップ手順に従ってください。

```bash
umask 077
backup_dir="./backups/paon-pre-7.1.0-$(date +%Y%m%d-%H%M%S)"
mkdir -p "$backup_dir"
docker compose exec -T db sh -c \
  'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > "$backup_dir/database.dump"
```

`pg_dump` が終了コード 0 で完了したことを確認します。アーカイブの目次は次のコマンドで確認できます。ただし、これは別 DB への復元確認の代わりにはなりません。

```bash
docker compose exec -T db pg_restore --list < "$backup_dir/database.dump"
```

バックアップに失敗した場合は、マイグレーションへ進まないでください。Redis のキューとアップロード済みメディアも保持し、通常のバックアップ対象に含めてください。

## 5. 全フェーズのマイグレーションを実行する

```bash
docker compose --profile setup run --rm --no-deps db-migrate \
  paon-migrate --all --acknowledge-contract
```

`--all` は `expand`、`backfill`、`validate`、`contract` を順に実行します。`--acknowledge-contract` は旧プロセスをすべて停止済みであることを確認し、旧カラム・テーブルの削除を含む最終フェーズを許可する指定です。

**引数なしの `paon-migrate` は既定で `expand` までしか実行しません。** 標準の `db-migrate` サービスや `task compose:db-migrate` を引数なしで実行するだけでは、7.0.x からの更新は完了しません。また、web・worker の起動時にマイグレーションが自動実行されることもありません。

`PAON_MIGRATION_PHASE` を設定している場合は、`--all` と併用できないため解除してください。`--target-version` は Mastodon のバージョンを指定するオプションです。この手順では指定不要で、Paon のバージョンである `7.1.0` は指定しません。

マイグレーションが正常終了したら、スキーマを確認します。

```bash
docker compose --profile setup run --rm --no-deps db-migrate \
  paon-migrate --check
```

終了コード 0 と `schema ok` を確認してから次へ進みます。

### 途中で失敗した場合

web・worker は停止したまま、エラーログを確認します。フェーズごとにトランザクションが分かれており、失敗したフェーズはロールバックされますが、それ以前に完了したフェーズは残ります。原因を解消した後、同じ `--all --acknowledge-contract` のコマンドで再開できます。

2要素認証の復号エラーでは、既存の `OTP_SECRET` と追加した暗号鍵が正しく渡っているかを確認してください。`MIGRATION_IGNORE_INVALID_OTP_SECRET=true` は対象ユーザーの移行をスキップするため、通常のアップグレード手順では使用しません。

## 6. 7.1.0 を起動して確認する

```bash
docker compose up -d --no-build --no-deps web worker
docker compose ps
docker compose logs --tail=100 web worker
curl --fail http://127.0.0.1:3000/health/ready
```

`--no-build` で取得済みのイメージを使い、コンテナを再作成します。`docker compose restart` では新しいイメージや環境変数が反映されないため、`up -d` を使用してください。`--no-deps` は PostgreSQL、Redis、Meilisearch が引き続き稼働している前提です。

コンテナが再起動を繰り返していないこと、web が healthy になること、readiness が成功すること、worker のログに起動エラーがないことを確認します。ポートを変更している場合は、確認先も読み替えてください。

最後にブラウザからログイン、2要素認証、タイムライン表示、投稿、検索を確認し、worker による配送・通知処理も確認します。`schema ok` と readiness の成功だけでは、これらの動作確認は完了していません。

## 7. 7.0.x に戻す場合

最終フェーズには旧カラム・テーブルの削除が含まれるため、**イメージだけを 7.0.x に戻すことはできません。** マイグレーションが途中で失敗した場合も、DB が変更前のままとは限りません。

1. 7.1.0 の全 web・worker と関連する書き込み処理を停止します。
2. アップグレード前の DB バックアップを、復元先を確認したうえで復元します。変更済み DB への単純な追加インポートは避け、変更後のオブジェクトが残らない形で復元してください。
3. 保存した Compose 設定・環境変数・旧イメージに戻します。
4. Redis のキューやメディアと復元した DB の整合性を確認してから、旧 web・worker を起動します。

DB の復元では、バックアップ取得後の投稿や設定変更は失われます。復元に備えて、旧設定と追加した暗号鍵を含む新設定の両方を保管してください。
